02 · WEEK 1

Deploy-as-change — the flagship

A push to production on a connected repo becomes a change request: scored, collision-checked, approved if risky, and its outcome recorded when the deploy finishes. Engineers never fill the form.

User stories

  • As an engineer, when I deploy to production from GitHub Actions, a change request appears with the commit/PR linked — I never fill the form.
  • As an approver, the auto-created change goes through the same scoring, collision detection and (if risky) the same Slack/email approval flow as a hand-filed change.
  • As an owner, when the deploy job finishes, the outcome (success/failed) is recorded from the deploy status — CFR feeds itself.

Technical design

PieceDesign
WebhookPOST /api/integrations/github/webhook — HMAC X-Hub-Signature-256 verification, reuses the existing rate limiter; workflow_run / deployment events only.
Repo connectionsNew github_connections table (repo, default systems, auto-submit threshold, secret) + admin UI on the Integrations page.
Mapping rulesDeploy env production → change type from changed paths / commit scope (fallback normal); deploy ref + run URL → description; deployer email → owner via existing email matching.
Outcome loopDeploy completes → record_post_change(success|failed) from the workflow_run conclusion — the "did it work?" loop closes itself for deploys.
IdempotencyUnique delivery_id per event — same pattern as the email Message-ID dedupe.
Duplicate safetyA deploy matching an open human-filed change on the same systems links to it instead of creating a duplicate.

Acceptance criteria

  1. Push to a connected repo → change created within 10 s, scored, systems attached, owner mapped.
  2. Risky auto-change → approvers get the same Slack DM with the "why".
  3. Deploy failure → post_change_result=failed; the CFR dashboard moves.
  4. Replayed webhook delivery → no duplicate change.
  5. Invalid signature → 401 + audit entry.

03 · WEEKS 2–3

Calendar sync & Microsoft Teams

Calendar sync (week 2)

Freezes and change windows appear on the calendars people already check.

  • Read-only out (day 1): GET /api/calendar/changes.ics — RFC 5545 feed of change windows + freezes, token-authenticated per user (users.calendar_token, refreshable). No external dependencies — this alone delivers most of the value.
  • Two-way write (rest of week): Google Calendar API + Microsoft Graph (OAuth; tokens in the settings table — same pattern as the Slack bot token). Changes create events; freezes create all-day events. Calendar errors never block the workflow (logged, retried by the existing sweep pattern).
  • Propagation: editing a change's window updates the linked event (calendar_event_id stored on the change).

Microsoft Teams (week 3)

The Slack approval experience, ported — same policy, same audit, new transport.

  • Azure Bot registration + Bot Framework; POST /api/teams/interactions validates the bot token against Azure's published OpenID metadata (cached) — the Slack-signature pattern ported.
  • Outbound proactive messages reuse the existing outbox shape (Notification.kind="teams") so the Approvals page renders Teams rows without new frontend logic.
  • Identity: users.teams_id; same email auto-link + ephemeral fallback as Slack.
  • Any-of policy, idempotency keys and delivery audit are literally the same service calls. Teams outage → the email fallback chain already built in v0.2.

Risks, success metrics & what's deferred

Top risks and mitigations

RiskMitigation
GitHub event variety (rename, re-run, skipped runs)Only two event types; unique delivery_id; unknown payloads rejected with 4xx, never 500
Calendar APIs eat the weekShip the .ics feed on day 1 — value exists even if OAuth write slips; two-way is a bonus
Azure bot registration friction (tenant, consent)Start registration in week 1 in parallel; demo on the Bot Framework Emulator until tenant consent lands
Metric definitions argued aboutDefinitions fixed in this PRD and printed on the Analytics page itself
Webhook attack surface growsEvery new webhook: signature verification + the existing rate limiter + idempotency — same as email

Success metrics (30 days after rollout)

  • ≥ 30% of changes auto-created from deploys; time-to-file < 30 s for deploy changes
  • ≥ 1 external calendar subscriber per team; zero workflow incidents caused by calendar outages
  • ≥ 20% of approvals decided from Teams in Teams-first shops
  • The analytics page becomes the most-screenshotted page in manager demos

Deliberately deferred

Billing/seats, compliance pack, SSO hardening, workspaces with per-team visibility, ML risk weights, Jira/ServiceNow sync, mobile push — v1.0 candidates; none block the operations story.
